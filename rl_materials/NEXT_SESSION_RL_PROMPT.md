확정본은 `data/case_rl/releases/rl-pilot-27fc35d39288134b`이다. 영수증과 manifest의 파일 해시를 검증하고 사용해라. 이것은 한국·미국 판례 각 20건을 검토한 파일럿이며 전체 판례 DB를 학습한 것으로 보고하지 마라.

- 채점 검증: calibration 20개 에피소드 및 해당 비교 자료.
- 최종 평가: test 20개 에피소드 및 해당 비교 자료.

정책에는 메시지·도면·제공된 판례 카드만 입력하고, 참조 답안·chosen/rejected 표지·검토 보고서를 섞지 마라. calibration/test의 답안과 선호 표지를 정책 또는 보상 모델 학습에 사용하지 마라. 채점 기준 조정과 체크포인트 선택은 calibration 범위에서 하고, 최종 test는 모델 선택을 마친 뒤 평가에 사용해라. 확정본은 덮어쓰지 마라.

학습 목표는 다음 세 가지다.

1. 도면에 근거한 독립항 1개와 종속항을 함께 작성한다. 확정본의 예시는 종속항 2개이며, 실제 출력은 근거가 있는 범위와 출력 계약을 따른다. 도면에 없는 기술 구성을 판례에서 가져와 추가하지 않는다.
2. 작성 시 제공된 판례 카드와 청구항별 적용 설명을 연결한다. 사건번호·법원·선고일·페이지·원문 해시는 카드 저장소와 `resolve_annotations`를 통해 확인한다. 모델 가중치 내부에서 어떤 판례가 답변을 유발했는지 증명했다고 주장하지 않는다.
3. 한국·미국 판례를 근거로 가상 사안에 대한 특허 자문을 제공한다. 관할·기준 시점·적용 법리·반대 논거·한계와 근거 인용을 포함하고, 서로 다른 관할의 법리를 혼동하지 않는다.

## 4. RunPod에서 실제 강화학습 실행

GPU를 켜기 전에 CPU에서 데이터 연결, 이미지 경로, 출력 계약, 보상 함수, 저장·재개·종료 절차를 준비해라. 기존 CPU 인코딩 검증과 자료 검토 통과를 GPU 학습 호환성 또는 모델 성능 검증으로 대신하지 마라.

내 RunPod 계정에서 실행해라. 실제로 지원되는 Gemma 멀티모달·PEFT 환경을 확인한 뒤 GRPO 등 생성 결과의 보상으로 정책을 업데이트하는 강화학습을 구현해라. SFT나 DPO만 실행하고 온라인 강화학습을 완료했다고 보고하지 마라. 실제 채점 백엔드를 별도로 연결하고, 보류된 calibration 비교에서 선호 판단 일치율 85% 이상과 심각한 오류 탐지 여부를 검증해라. 이전 자료 검토의 24/24 결과를 새 채점 백엔드의 검증 결과로 재사용하지 마라.

GPU 종류·수량·시간당 요금·예상 소요 시간·예상 총비용·최대 실행 시간과 비용 중단 한도를 착수 기록에 명시해라. 기존 예산 제한이 있으면 우선 적용하고, 필요한 최소 구성의 학습 Pod 하나로 시작해라. 비용 상한을 넘기는 증설·장기 실행·유료 서비스 추가에는 별도 승인을 받아라. 자동 충전으로 실행 범위를 늘리지 마라. 세션이 끊겨도 중단 한도가 작동하도록 외부 종료 수단을 준비해라.

짧은 실행으로 도면 입력, v2 로딩, 보상 계산, 역전파, 체크포인트 저장을 검증한 뒤 제한된 파일럿 학습을 진행해라. 유효한 생성 결과·보상·loss·학습 step·파라미터 변경을 기록해라. JSON 형식이나 인용 개수만 높이는 보상을 사용하지 마라. 실패 원인을 해결하지 않은 채 GPU를 켜 두거나 같은 유료 실패를 무한 반복하지 마라.

기존 v2와 새 모델을 동일한 입력·생성 조건에서 비교해라. 청구항의 도면 근거와 종속관계, 판례 인용 정확성, 어노테이션 연결, 자문 내용, 형식 준수와 반복·환각을 평가해라. 소규모 파일럿 결과를 일반적인 법률 자문 능력의 보장으로 보고하지 마라.

## 5. 먼저 Hugging Face에 저장하고 복구 가능성을 검증

새 모델은 내 Hugging Face의 별도 **비공개** 저장소에 저장해라. 새 저장소 이름은 `Mepeng22/gemma-4-31b-claim-rl-v3`를 우선 검토하되, 이미 존재하는 무관한 저장소를 덮어쓰지 말고 충돌 없는 이름을 사용해라. 기존 v2 원본은 보존해라.

어댑터 또는 병합 모델, 설정, 필요한 토크나이저·프로세서 파일, 실제 기반 모델과 v2 리비전, 학습 재료 manifest, 학습 설정·로그·평가 결과·모델 카드와 필요한 재개 상태를 저장해라. 학습 완료 전에 중단되면 가능한 마지막 체크포인트와 실패 기록도 보존해라.

서빙용 산출물에는 기존 v2와 이번 RL의 변경이 모두 반영되어야 한다. v2가 별도로 있어야만 작동하는 RL 차이분만 올리고 완성 모델이라고 하지 마라. 병합·누적 어댑터·양자화 중 사용하는 방식을 명시하고, 기존 서빙 엔진에 필요한 변환도 학습 자원을 정리하기 전에 끝내라.

원격 업로드 완료 응답만으로 끝내지 말고, Hugging Face의 고정 commit SHA와 파일 해시를 확인하고 새 경로에 내려받아 실제 모델을 다시 로드·추론해 복구 가능성을 검증해라. 이 검증 전에는 유일한 체크포인트가 들어 있는 Pod나 볼륨을 삭제하지 마라.

## 6. 학습 과금 자원 종료 후 기존 서버리스의 모델 교체

**Hugging Face 저장·재로드 검증 → 학습용 과금 자원 종료 → 기존 서버리스 새 모델 교체** 순서를 지켜라.

학습 Pod는 Stop 상태로 남겨 두지 말고 Terminate/Delete하여 종료를 확인해라. 이 프로젝트의 학습·평가·변환을 위해 만든 GPU Pod, 임시 엔드포인트, 남은 유료 디스크·네트워크 볼륨·상시 워커를 확인하고, 백업 검증 후 불필요한 자원을 정리해라. 재시작 예약과 워커를 계속 깨우는 자동화도 해제해라. RunPod 자동 충전(Auto-pay)이 켜져 있으면 끄고 상태를 확인해라. 자동 충전 해제와 리소스 과금 종료는 각각 검증해라. 다른 프로젝트의 자원이나 계정·잔액·결제수단은 임의로 삭제하지 마라.

이후 기존 엔드포인트 `fdiltabt78bogm`을 유지하면서 새 RL 모델로 교체해라. 먼저 현재 설정과 기존 v2 리비전을 복구 가능하게 저장하고, 비밀값은 보고서에 넣지 마라. 현재 서빙은 마지막 기록상 `cyankiwi/gemma-4-31B-it-qat-AWQ-INT4` 기반의 INT4+LoRA 구성이므로, 새 어댑터의 호환성·rank·타깃 모듈을 실제로 확인해라. 기존 설정을 맹목적으로 재사용하지 마라.

새 Hugging Face commit에 고정하여 실제 RL 가중치를 로드하도록 설정해라. 설정에 모델 이름만 바꾸는 것으로 완료하지 마라. 워커 로그와 실제 응답을 통해 새 모델이 로드되었고 기반 모델로 조용히 대체되지 않았는지 확인해라. 새 모델이 배포 검증에서 실패하면 정상 v2로 복구하고 원인을 보고해라. 유효한 새 모델의 배포가 완료되지 않았는데 전체 작업을 완료 처리하지 마라.

엔드포인트는 요청 때 실행되는 Flex 방식으로 두고, Active/min workers=0, max workers=1, 지원되는 짧은 idle timeout을 적용해라. 테스트 후 실제 실행 중 워커가 0으로 내려가는지 확인해라. 불필요한 유료 네트워크 볼륨과 상시 실행 설정은 남기지 마라. **서버리스는 호출·기동·처리·종료 전 대기 동안 사용료가 발생할 수 있다. “사용해도 완전 무료”라고 보고하지 말고, 종료한 학습 비용과 남는 요청 기반 비용을 구분해라.**

## 7. 내가 바로 테스트할 수 있게 마무리

`serving/claim_client.py`, `space/test_ui.py`, `serving/launch_test.py`, `start-test.cmd`의 현재 구조를 확인하고 새 모델을 기본값으로 연결해라. 로컬 테스트 화면 `http://127.0.0.1:7860/`에서 독립항·종속항 작성, 판례 어노테이션, 판례 기반 자문을 입력·확인할 수 있게 해라. 판례 정보는 검증된 카드 데이터와 연결해서 표시해라. 각 기능을 실제 엔드포인트 요청으로 검증해라.

끝나면 `HANDOFF.md`와 실행 결과 보고서에 다음을 남기고 내게 알려줘.

- 출발 v2 리비전 → RL 실행 → 새 Hugging Face 저장소·commit SHA의 연결.
- 실제 강화학습 방식, GPU·학습 시간·step·비용. 비용 확정 전이면 추정값과 그 근거.

- 종료한 Pod·볼륨·임시 엔드포인트의 ID, 자동 충전 상태, 남은 과금 가능 자원.
- 기존 서버리스 ID, 배포한 새 모델·리비전, 테스트 결과와 최종 워커 수 0 확인.

실행 중 문제가 생겨도 GPU와 저장소를 켜 둔 채 종료하지 마라. 복구할 산출물을 먼저 보존하고 작업용 유료 자원을 정리한 뒤, 완료하지 못한 단계와 필요한 조치를 정확히 보고해라.
